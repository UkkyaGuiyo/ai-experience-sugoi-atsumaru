# AI作業の一般化ノウハウ候補

**状態：独立レビュー待ち。正式なKnowledge Entryではない。**

この文書は、許可された調査から着想した方法論の提案を、人物・組織・元案件・元記録を識別できない形に一般化したレビュー資料である。原資料の匿名化コピーや実験報告の移植ではない。候補を採用済みの規則、実証済みの成功例、作業実行の許可として扱わない。root AGENTS.mdと既存の安全規則が引き続き適用される。

全候補の根拠区分は **inference**、今回の再現状態は **not reproduced**、一般化した効果への確信度は **low**。元記録に検証結果が存在しても、この候補そのものの再現・独立レビューを済ませたことにはしない。本文の検証例は、将来の評価用に新しく組み立てた合成例であり、実行済み結果ではない。

人物名、所属、元案件名、個人URL、非公開URL、元ファイルパス、元コミットやデータのハッシュ、実行日時、実測値、生会話、生ログ、第三者コードは保存していない。モデルやツールの版数も推測していない。提案作成者による保存前の内容確認と機械検査は、独立レビューの代わりにはならない。

## 候補A：現行指示を一意の入口にし、矛盾を含む例で検査する

**対象・失敗型：** 長期エージェント作業で、過去の引き継ぎと現行指示が同じ文書に残る。期待する単語が文書のどこかにあるだけで合格にすると、古い指示や反対の指示を採用し得る。

**再利用する手順：** 最初に読む場所に現行の指示先を一つ示し、過去の記録を実行対象から分離する。自動検査では現行セクションの位置、見出し、対象文書、必須条件、禁止条件を確認する。履歴を都合よく書き換えるのではなく、現行と履歴の役割を明示する。

**検証例：** 正しい語句を残したまま、架空の古い指示を先頭へ追加する。「任意」と「必須」が同居する矛盾した現行文を作る。どちらも合格しないか調べる。

**適用と限界：** 複数セッションや担当交代がある作業に向く。文字列・見出し検査は指定した形式しか保証せず、任意の自然言語の意味や現在の実行環境を保証しない。

**想定分類：** agents / context management。既存EXP-000001の結果区分ではなく、実行前の指示選択を扱う。

## 候補B：観測できない状態を「存在しない」に変換しない

**対象・失敗型：** ツール検索、プロセス確認、資源確認で、空結果が返る。権限不足、対象範囲の不足、取得失敗、古い結果でも空に見えることを考慮せず、後続操作を始めてしまう。

**再利用する手順：** 確認結果を「存在」「確認範囲内で不在」「不明」に分ける。不在には、問い合わせ成功、対象範囲の充足、十分な鮮度が必要だと定義する。不明は不明のまま扱い、必要な条件を満たすまで、その条件に依存する操作だけを保留する。無関係な作業まで一律に停止しない。

**検証例：** 同じ空リストに対して、取得成功、権限不足、一部結果のみ、期限切れの状態を与える。すべてを同じ不在結果へ潰さないか確認する。

**適用と限界：** 起動、削除、上書き、共有資源の取得前に有用。全世界での不在証明ではない。観測を増やすための無断の権限昇格、個人情報の取得、別作業への干渉は認めない。

**想定分類：** patterns / tool-result interpretation。既存EXP-000002の範囲限定を、空結果の解釈へ具体化する候補。

## 候補C：安全性を確認するテスト自体の副作用を封じる

**対象・失敗型：** 純粋なテストのつもりで、実際のOS操作や情報取得を行う古い関数を呼ぶ。安全な新経路を追加しても、既定経路や別の呼び出し元から従来の取得処理が残る。

**再利用する手順：** 実行前に入口から外部操作までの呼び出し経路を確認する。判定処理と実取得処理を分離し、判定テストにはメモリ内の合成値だけを渡す。外部操作を禁止したテストでは、呼ばれたら即座に失敗する代替アダプターを注入する。既定・旧・回復経路も対象にし、判定後ではなく取得前にデータ最小化を適用する。

**検証例：** 取得アダプターが呼ばれると失敗する合成テストを、通常経路と旧経路の両方へ通す。架空の数値を実OS識別子として渡す方法は使わない。

**適用と限界：** Computer Use、ネイティブ連携、外部API、情報収集の境界に向く。合成テストの成功は実環境での正常動作の証明ではなく、実取得テストには別の許可と最小取得設計が必要。

**想定分類：** anti-patterns / verification safety。既存EXP-000003の一時ファイル所有権とは別に、検証時の情報取得と実行境界を扱う。

## 候補D：必須能力を先に検証し、別機能で成功を代用しない

**対象・失敗型：** 製品の中核に未確認の能力があるのに、周辺機能や見た目の実装を先行する。難所に遭遇すると、要件と異なる代替出力を無断で成功扱いする。

**再利用する手順：** 必須条件、許容できる代替、許可されない代替を分ける。中核能力だけを確かめる最小の検証を作る。APIの存在、目的の実行環境への公開、コンパイル、呼び出し、必要な出力の取得を順に確認する。未確認・実行不能・失敗を分け、経路変更や要件変更は別の判断として記録する。

**検証例：** 架空の取得機能について、型定義だけ存在する、呼べるが空値、実値を取得できる、という状態を用意する。型の存在や別方式で作った値だけでは中核要件を合格にしない。

**適用と限界：** SDK制約や外部環境に依存する企画に向く。限られた経路の失敗から全方式の不可能を断定しない。優先度付けの提案であり、開発時間の短縮効果は今回測定していない。

**想定分類：** workflows / feasibility planning。既存EXP-000001・EXP-000002と関連するが、ここでは実装順序と要件の無断置換防止を扱う。

## 候補E：観測から区別できるかを、二つの合成履歴で先に問う

**対象・失敗型：** 限られたセンサー値やツール出力から、必要な相手・対象・状態を区別できると仮定し、複雑なエージェント連携や追跡処理を組む。

**再利用する手順：** 正解が異なる二つの仮想状況を作り、判断側に渡る初期状態と観測履歴を比較する。両方が同じなら、その情報だけを使う決定的処理は異なる判断を選べない。必要な追加観測を明示するか、不明を表示して危険な自動判断を拒否する。識別情報を増やす場合も、プライバシー・許可・必要最小性を別途満たす。

**検証例：** 同じ内部状態から始まり、同じ出力列を受け取るが、最後の正解ラベルだけが違う二つの合成履歴を用意する。追加の区別可能な入力がある対照例と比較する。

**適用と限界：** 対象選択、追跡、照合、状態推定の実装前に有用。この反例は定義した観測条件に限られ、他の観測源、全構成、実環境の挙動を否定するものではない。実在する人物の追跡データは使わない。

**想定分類：** patterns / experiment design。既存EXP-000002の一般的な範囲限定に対して、区別可能性を試す具体的な反例設計を追加する。

## 候補F：件数や並び順の一致を、意味上の対応の証明にしない

**対象・失敗型：** インポート、変換、集計で、要素数、表示名、配列の位置だけを使って入出力を対応付ける。順番が変わっても件数が同じなら成功に見えてしまう。

**再利用する手順：** 何を同一と見なすかを明示し、処理対象の意味を保つ識別子や内容上の対応を用いる。曖昧な対応は未確定のまま残す。期待する結果から対応表を逆算して同じ表を正解判定にも使わず、対応を決める根拠と検証の根拠を分離する。

**検証例：** 要素の順番だけを入れ替える、件数を保ったまま内容を交換する、同じ名前で内容を変える、重複要素を置く、といった合成例を用意する。偶然一致した並び順を固定の変換規則にしない。

**適用と限界：** データ移行、3D変換、参照の付け直し、表の結合に向く。量子化、正規化、重複がある場合の一致判定には限界があり、内容一致だけでは別の意味属性まで証明できない。

**想定分類：** patterns / semantic preservation。既存EXP-000003とは異なり、ファイル処理ではなく変換結果の対応関係を扱う。

## 候補G：検査条件を作業段階に結び付け、例外を全体へ広げない

**対象・失敗型：** テンプレート確認、依存関係の配置、解決後の確認に同じ必須条件を適用する。まだ生成されないものを早すぎる段階で要求し、回避のために検査全体を緩めてしまう。

**再利用する手順：** 各段階で存在すべきもの、後段まで未確定でよいもの、常に禁止するものを別々に定義する。延期できる条件は対象と段階を限定し、後段で必ず確認する。未知の対象、不正な参照、段階不明を広い例外で通さない。安全制約を外す変更とは分離してレビューする。

**検証例：** 許可された依存物が配置前にだけ未存在である例、未許可の依存物、許可名だが場所が違う例、配置後も未存在の例を用意する。早い段階の延期が後段の合格へ引き継がれないか確認する。

**適用と限界：** ビルド、配布、依存解決、移行パイプラインに向く。これは安全確認の免除ではなく、必要な確認時点の明確化。段階遷移の証拠がなければ、実行可能とは判定しない。

**想定分類：** workflows / phase-aware validation。既存EXP-000001が結果の分離を扱うのに対し、ここでは段階ごとの条件と限定的な延期を扱う。

## 候補H：「検査だから読み取り専用」と仮定せず、所有する検証物を使う

**対象・失敗型：** 検証画面、インポート、再バインド、補助APIの呼び出しで、利用者の資産や設定まで変わる可能性を見落とす。既存の資産を手近なテスト素材として使ってしまう。

**再利用する手順：** 検査の呼び出し経路と副作用を調べる。必要なら、自作した最小の使い捨て検証物と隔離した作業場所を使い、操作対象をその範囲へ限定する。操作前後の保護対象の状態を比較する。メモリ上の成立、保存、再読込後の成立を分け、クリーンアップは所有を確認できる対象だけに行う。

**検証例：** 保護対象を変える検査アダプターと、所有する検証物だけを変えるアダプターを用意する。終了後に保護対象の変更を検出できるか確認する。合成値だけで本番資産の互換性を証明したとは扱わない。

**適用と限界：** Editor操作、生成物検証、インポート、GUI自動化に向く。隔離は完全なサンドボックスではない。第三者資産の複製、既存データの上書き、公開・アップロードは別の許可なしに行わない。

**想定分類：** patterns / non-destructive verification。既存EXP-000003の所有権原則を、生成物・保存・Editorの副作用へ拡張する候補。独立レビューで重複が大きいと判断した場合は新規採用せず、既存項目の拡張を検討する。

## 候補I：ファイルの分業と、共有実行環境の利用を別々に管理する

**対象・失敗型：** サブエージェントごとにブランチや編集ファイルを分けたため、Editor、実行プロセス、出力先、計測環境も独立したと考えて同時利用する。

**再利用する手順：** ファイルの担当範囲と実行資源の担当範囲を別に定める。共有実行資源には調整役を置き、対象インスタンス、許可された作業、取得・解放条件を確認してから利用する。実行待ちの間は、共有資源に触れない調査や合成テストを進める。他担当の接続先を無断で切り替えたり、広い名前一致でプロセスを停止したりしない。

**検証例：** 二つの作業者が異なるファイルを編集しながら、同じ実行資源を要求する合成例を作る。片方だけに利用を許可し、古い所有情報や不明な対象では開始しないことを確認する。

**適用と限界：** 複数エージェント、GUI操作、共有Editor、実機テストに向く。単なる文書上の担当指定は排他制御そのものではない。性能改善や待ち時間削減の実測結果はなく、独立した資源まで一律に直列化する提案ではない。

**想定分類：** agents / shared-resource coordination。既存EXP-000003の一時ファイル対策とは区別し、実行資源の所有と実行タイミングを扱う。

## 重複整理

EXP-000001の「検証結果を段階ごとに分ける」、EXP-000002の「調べた範囲を超えて結論を広げない」、EXP-000003の「一時ファイルの所有と読み込み前のソース確認」を、同じ内容の新規Entryとして追加しない。上の各候補にも関連原則が含まれるため、独立レビューで追加の実用価値がないと判断したものは統合または不採用にする。

## 正式収録に進める条件

- 別のReviewerが、内容、安全性、一般化の妥当性、根拠区分、既存項目との差分を確認する。現時点では未実施。
- 必要な検証は、別途許可された合成例または安全な公式資料で行う。元案件の識別情報や生記録をこのRepositoryへ持ち戻さない。
- 調査・設計からの推論を実験済みに格上げしない。観測日やモデル情報を推測で埋めない。安全に必要項目を満たせない候補は収録しない。
- 採用分だけ最新Schemaに変換し、既存IDを再確認して採番する。未確認の承認フラグを埋めず、Validator、tests、独立レビューを経て承認済み運用で統合する。
